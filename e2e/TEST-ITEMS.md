# E2E テスト項目

[README.md](README.md) の環境(Zed + IME + `fifty_four_lsp` を仮想ディスプレイ上で動かす)で、
**キー入力 → 画面変化**として確かめたいことの一覧。ハーネス(`e2e/src/`・`e2e/tests/`)は A(起動)だけ実装済みで、
ここは「何を確かめるか」の台帳であり、実装の順序づけの元になる。

**載せる基準**: LSP の単体テスト(`cargo test`)で返り値を検証済みのものは入れない。E2E で確かめるのは次の 3 種類だけ。

1. **結線**: Zed が実際にその LSP 機能を呼び、結果を画面に反映すること(capability の宣言、言語の自動認識、
   Zed 側の設定 `inlay_hints.enabled` など。欠けると**黙って何も起きない**ものが多い)
2. **競合**: 起動直後・編集中の、プロセス間・メッセージ間のタイミング依存(辞書の構築と `didOpen`、IME の変換中の更新など)
3. **クライアントの挙動への依存**: ファイルのリネーム(`workspace/applyEdit`)、`didRenameFiles` の送信、補完メニューのフィルタなど、
   Zed の実装次第で変わるもの

表示サーバごとに挙動が違うもの(X11 の XIM と Wayland の text-input-v3)は、表の「表示」列で分ける。

## 読み方

| 列 | 意味 |
|---|---|
| ID | `<分類><連番>`。テスト名・スクリーンショット名にそのまま使う |
| 表示 | `X` = X11、`W` = Wayland。両方で通すものは `X W` |
| 観測 | 何を見て判定するか。`画面` = スクリーンショット、`ログ` = `Zed.log` など、`DBus` = fcitx5 の状態、`ファイル` = ワークスペース内のファイル |
| 状態 | `確認済み` = 手で動かして通った(日付つき) / `未確認` / `要調査` / `要LLM` = 偽の LLM サーバが前提 |

## 優先順位

1. **P0 スモーク**(A): これが落ちたら他は意味がない。毎回回す
2. **P1 ハイライト**(B): 起動直後の競合だけを見る。中身は単体テストで検証済み
3. **P2 結線と Zed 依存**(C・D): Zed の設定・挙動に依存する部分だけ。準備するワークスペースが増える
4. **ハーネス自身**(E): 失敗の診断と入力経路が壊れていないか
5. **後回し**(F): 文章品質診断の経路(Q)と LLM 依存(L。偽 LLM が先に要る)

IME・日本語入力そのものは Zed と fcitx5 の領域で、この LSP の試験対象ではない。
ただし全項目が「キーを打って結果を見る」ので、入力経路が生きていることだけはハーネスの項目(E)で確かめる。

## A. 起動(P0)

実装: `e2e/tests/a_startup.rs`(Rust。ホストからコンテナを `exec` で操作する)。実行は `cargo e2e`(ルートから)(README「テストの実行」参照)。

| ID | 表示 | 項目 | 判定方法 | 状態 |
|---|---|---|---|---|
| A01 | X W | コンテナが ready になる | `e2e-status` が `ready`、`e2e.log` に ready の行。起動に失敗したら(`failed:`・時間切れ)、その理由を A01 の FAIL として出す。他の試験は「A01 を参照」で失敗する | 実装・確認済み(2026-11-03、wslc) |
| A02 | X W | Zed の窓が出る | スクリーンショットを撮り、色数が 64 以上で最頻色が画面の 97% 以下(実画面は 3000 色超・約 73%。紺一色・真っ黒は 1 色・100%) | 実装・確認済み |
| A03 | X W | `.txt` が `FiftyFour` 言語になる | `Zed.log` の LSP 起動行で代用(この LSP は拡張が持つ FiftyFour のバッファにしか起動しないため。ステータスバーの OCR はしない) | 実装・確認済み |
| A04 | X W | LSP が起動して落ちない | 先に**肯定的な信号**を待つ(起動行 + プロセスが居る + 起動時に作る DB `/usr/local/bin/db/fifty_four.db`)。その後 4 秒待ち、生存と `panicked`・`Failed to start language server` の不在を確かめる(「落ちたログが無い」だけだと、起動前に調べて素通りする) | 実装・確認済み。`db` を書けなくしたイメージで FAIL になることを確認(2026-11-03) |
| A05 | X W | 拡張が読み込まれる | `Zed.log` の `extensions updated. loading N`(N ≥ 1) | 実装・確認済み |
| A06 | X W | 遅い環境・同時起動でも起動できる | `E2E_PARALLEL=N` のときだけ、N 本を同時に起動して全部が ready になるか | 実装済み(未実行)。Wayland は A07 の問題で全数は通らないことがある |
| A07 | X W | 起動し直さずに済む | entrypoint が起動し直した回数(`/out/zed-attempts`)が 1。2 以上なら **WARN**(`E2E_STRICT_A07=1` なら FAIL) | 実装済み。**Wayland で Zed が panic する問題が未解決**(README「調べてわかったこと」) |

ハーネス自体が失敗を検出できることも確認済み: `E2E_ZED_WINDOW_TIMEOUT=0` で A01 が FAIL、`db` ディレクトリを書けなくしたイメージで A04 が FAIL。

## B. セマンティックハイライト(P1)

トークンの中身(括弧・ルビ・キャラ名・見出しの種別と token type の対応)は LSP の単体テストで検証済みなので、
E2E では見ない。E2E で見るのは、**Zed に実際に色が載ること**と、**起動直後の競合**だけ。

IPADIC の辞書構築は debug ビルドで数百 ms〜数秒かかり、`Backend::new()` ではバックグラウンドに回している
(`highlight.rs`)。Zed のワークスペース復元(タブの一括 `didOpen`)と競合すると、色が付かないタブが出ることが
過去に実測されている。遅い環境(wslc)ほど出やすい。

準備: 台詞・ルビ・`characters.md` のキャラ名を含む `.txt` を複数用意し、それらをタブで開いたまま Zed を終了・再起動できるワークスペース。

## D. plot.md と章(P2)

## F. 後回し(重いので当面やらない)

どちらも準備が重い。品質診断はルールの中身が単体テストの範囲なので、E2E では「診断が Zed に届き、編集に追従する」ことだけを見る。
LLM 依存は偽の LLM サーバが先に要る。

### 文章品質診断

各ルール(括弧不一致・三点リーダ・い抜き/ら抜き・二重敬語・冗長表現・「の」連鎖・長文・slop など)の判定は単体テストで検証済み。
E2E ではルールを 1 つだけ選んで(`Q01` は確認済みの「主題を示す「は」が 1 文中に 2 回」)、診断の経路を見る。

| ID | 表示 | 項目 | 手順 | 期待 | 観測 | 状態 |
|---|---|---|---|---|---|---|
| Q01 | X W | 診断が Zed に届き、画面に出る | 「吾輩は…吾輩は…」のように 1 文に「は」を 2 回書く | 波線が付き、ステータスバーに「主題を示す「は」が1文中に2回使われています」 | 画面 | 確認済み(X11 のみ 2026-11-03)。Wayland は同じ操作で波線・文言が出ていなかった(撮影が早すぎた可能性あり) → 要調査 |
| Q02 | X W | 直すと診断が消える | Q01 の「は」を 1 つ消す | 波線とステータスバーの文言が消える(発行と取り下げの両方) | 画面 | 未確認 |
| Q03 | X W | 日本語の途中への挿入・複数行編集に追従 | 診断の付いた文の前に文字を挿入。改行を足して上の行を編集 | 波線が元の語に付いたまま動く(UTF-16 の位置と増分同期が Zed の実際の編集で崩れない) | 画面 | 未確認 |
| Q04 | X W | 変換中に診断が暴れない | 変換中(確定前)に診断が点滅・消失しない | 確定時に 1 回だけ更新される(IME + `didChange` の組み合わせ) | 画面 | 未確認 |
| Q05 | X W | 設定でルールを無効化できる | `initialization_options.quality.rules` で Q01 のルールを無効にして起動 | Q01 の入力で診断が出ない(`lsp.fifty-four.initialization_options` の下にネストしないと Zed が黙って無視するため、設定の経路ごと見る) | 画面 | 未確認 |

### LLM 依存(要 偽 LLM)

偽の LLM サーバ(決まった応答を返す)を用意してから。実際のモデルを使うと結果が毎回変わる。
候補の整形(句読点の付与・除去、改行、長い候補の短縮)は単体テストの範囲。E2E で見るのは、
**Zed が候補をどう表示・採用するか**(フィルタ、コミット文字、メニュー)と、Zed の `workspace/applyEdit` の扱い。

## 試験に入る前に決めること

1. **ワークスペースの用意**: 項目ごとに初期のファイル一式(`test.txt` / `characters.md` / `plot.md` …)を持たせ、
   試験の間で状態を持ち越さない。コンテナを試験ごとに起動し直すのが一番単純だが、起動に数秒〜数十秒かかる。
2. **待ち合わせ**: 診断・inlay hint は LSP の応答後に出る。固定の `sleep` ではなく、
   `Zed.log` の LSP ログ(span)か画面の変化を待つ条件にしたい(README の「未実装」項目)。
   Q01 の Wayland で波線が出ていなかったのは、これが無いことの実例かもしれない。
3. **判定方法**: 画面の完全一致(基準画像との差分)は、フォント・サイズ・テーマを固定してあっても
   アンチエイリアスやカーソル位置で揺れる。まずは領域を切り出して比較するか、
   ステータスバーなど文字列を OCR で読む方法を検討する。
4. **偽の LLM サーバ**: 後回しの L 群(LLM 依存)の前提。決定的な応答を返し、呼ばれた回数とプロンプトも記録できると、
   プロンプトに入る文脈(`{{PROGRESS}}`・キャラ設定)の検証にも使える。
5. **Wayland の差**: X11 と期待が違う項目が出たら、表の「表示」列で行を分けて書く。
